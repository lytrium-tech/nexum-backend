# Nexum V1.7 - FIFO 500 Stacktrace Debug

## 1. Context

A 500 Internal Server Error was observed when the frontend attempted to confirm a FIFO payment (e.g. 120,000 COP) against an obligation that had multiple overdue/pending periods. 

## 2. Stacktrace Captured

```text
POST /api/v1.7/obligations/6bc0a496-a01a-4fbf-9142-1f7f344d66b4/payments HTTP/1.1" 500 Internal Server Error

asyncpg.exceptions.UniqueViolationError: duplicate key value violates unique constraint "ix_obligation_payments_user_idempotency"
DETAIL:  Key (user_id, idempotency_key)=(ac77071d-524e-44e6-bf96-096931559ee4, 75954d4b-6321-4d7a-ade9-92c50b9a217b) already exists.
```

## 3. Root Cause

The `pay_obligation_fifo` function in `app/obligations/service_v17.py` splits the total payment `amount` into multiple slices (one for each applicable period). 

When inserting the corresponding `ObligationPayment` records into the database in a loop, it assigned the **exact same** `data.idempotency_key` to every payment slice. Since the database enforces a unique constraint on `(user_id, idempotency_key)`, the second payment insert in the same FIFO transaction failed with a `UniqueViolationError`, causing the 500 crash and rolling back the transaction.

## 4. Fix Applied

1. **Suffix in Loop**: We now append the `period_id` to the idempotency key in the creation loop:
   ```python
   idempotency_key=f"{data.idempotency_key}-{p.id}"
   ```
   This guarantees uniqueness across the multiple slices generated by a single FIFO call, while preserving the core idempotency ID passed by the client.

2. **Prefix Matching in Check**: The early idempotency check at the top of the function was updated to use `.like()` matching so it correctly identifies existing slices that start with the parent idempotency key:
   ```python
   ObligationPayment.idempotency_key.like(f"{data.idempotency_key}-%")
   ```
   This accurately returns a 409 Conflict if the client retries the same FIFO request.
